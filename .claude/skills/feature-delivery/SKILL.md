Use for consequential shared contracts, meaningful default-output semantics, data formats, production decoder/rendering math, release-sensitive behavior, or explicit invocation of this workflow; bounded changes stay with the main agent.
---

Use this workflow for substantial changes to shared cross-component contracts/core behavior, meaningful default-output semantics, persisted/interchanged data formats, decoder interpretation or rendering math, release-sensitive behavior, or when explicitly requested to use feature-delivery/an independent pair. Pure discussion/research alone does not trigger paired delivery. File count alone does not make a change substantial. Internal tools, documentation and diagnostics normally stay with the main agent unless they affect shared core or persistence semantics.

For other bounded work, the main agent implements directly, runs relevant tests and one appropriate actual-path check (for example a CLI operation, rendered view or document check). Do not start peers, model discovery or a full-suite ritual for that path. Consult [workflow.md](references/workflow.md) for boundary examples.

When this workflow applies, announce its use once. If assigned a delegated implementer/reviewer role, follow that role and return to the coordinator; do not recursively start this workflow.

The main agent stays coordinator: clarify requirements, dispatch work, integrate, run acceptance checks, and manage release. Keep its model unchanged. Create separate agent contexts for implementer and design partner; the same design partner later reviews. Separate contexts can use the same model. Never substitute roleplay in one context for independent review. If independent contexts are unavailable, report that limitation and stop implementation until a real peer route is available.

1. Read [workflow.md](references/workflow.md). Establish acceptance criteria, scope, release target/channel, and a short durable task record before dispatch. Existing authorization persists; an implementation request does not itself authorize publication or deployment.
2. Read only the applicable section of [runtimes.md](references/runtimes.md). Detect actual runtime tools, model availability and capacity. Use the editable installed profile, or [default.json](profiles/default.json). Model IDs belong in profiles, never this file. Report requested versus selected models and any fallback explicitly. A null profile means runtime configured default, not automatic inheritance of the coordinator's current model.
3. Have implementer and design partner discuss concrete interfaces, ownership and tests. The implementer must receive explicit design agreement before editing implementation. Use direct messaging where supported, coordinator relay otherwise. Preserve both peers through design and review iterations.
4. Implementer codes and self-tests handoffs and commits in this paired workflow. The design partner becomes reviewer, reviews the actual revision and tests, and returns actionable findings. Iterate until findings close. Escalate disputed design or repeated no-progress to the coordinator; do not silently waive findings.
5. After pair closure, the coordinator integrates and checks the real user path against acceptance criteria. Substantive changes to affected core logic/contracts require affected re-review and relevant checks, not a restart of the whole approval. The coordinator can integrate typos, documentation and test-expectation corrections that preserve the asserted behavior with a bounded check; they do not invalidate unrelated approval. Report evidence and limitations, then release only to the agreed authorized target.

Constrain parallel pairs by available slots. Isolate editing work in worktrees or explicit non-overlapping interface ownership; serialize shared browser, simulator and device use. A coordinator plus one pair fits three contexts. Do not promise concurrent pairs when capacity cannot support them.
